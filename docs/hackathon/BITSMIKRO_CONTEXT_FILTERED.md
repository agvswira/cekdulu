# 1. Competition Context

Competition name:

**BITSMIKRO INNOVATIVE VIBECODE 2026**

The competition focuses on building an innovative digital solution using:

- AI-assisted development / vibecoding;
- problem solving;
- functional implementation;
- effective use of AI;
- clear communication of the idea and product.

The intended output is a **deployed web application**.

The competition is not only about producing code. The official materials also emphasize:

- identifying a meaningful problem;
- designing a relevant solution;
- using AI effectively;
- building a functional product;
- presenting and demonstrating the product clearly.

# 4. Core Product Requirements

The product must be a:

**Web application / website**

Key requirements:

- must be developed during the competition period;
- must be original;
- must not be plagiarized;
- must be deployed;
- must have an accessible deployment link;
- must use AI as part of the vibecoding/development process;
- must include documentation of AI prompts/workflow;
- must use at least **one AI technology as a feature or major component in solving the chosen problem**.

Participants may use any:

- programming language;
- framework;
- development platform;
- AI tool;

as long as the product remains a web application and follows the vibecoding context.

# 5. AI Requirements

AI appears in the competition in two distinct ways.

## 5.1 AI during development

AI tools are expected to be used as part of the vibecoding workflow.

Participants must preserve documentation of the prompts/workflow used during development.

The judging rubric explicitly scores:

**Prompting Quality — 20%**

This means the prompting history is part of the competition artifact, not merely an internal development aid.

## 5.2 AI inside the product

The Technical Meeting states that each team must use at least:

**1 Artificial Intelligence technology as a feature or major component in solving the problem.**

Examples may include functionality that:

- calls an external AI API;
- processes AI-generated data;
- uses an LLM;
- uses another AI service.

The exact implementation is not restricted to a specific provider or model.

# 6. Backend / Server-Side Clarification

The Technical Meeting contains this rule:

> “Aplikasi yang dibuat hanya sebatas tampilan (Front-End), adanya tambahan arsitektur Back-End tidak akan menjadi nilai tambah.”

Additional Q&A clarification explains how this should be interpreted.

## What does NOT add score

Building backend infrastructure by itself does not provide extra points.

Examples:

- creating a Node.js server;
- creating a PHP server;
- creating a Python server;
- building your own REST API;
- building your own database;
- building your own authentication system;
- managing private server infrastructure.

The infrastructure itself is not a judging advantage.

## What IS still scored

Product functionality that happens to use server-side processing or external services **is still judged**.

Examples:

- fetching data from an external API;
- calling an AI API;
- using AI-generated results;
- using server-side communication required for a feature.

Therefore:

**Do not avoid useful AI/API functionality just because it uses server-side communication.**

The competition does not reward backend architecture for its own sake, but it still rewards useful product functionality.

---

# 7. Platform / Responsive Clarification

The website does **not** have to support every platform or screen size.

Participants are allowed to optimize primarily for:

- desktop only; or
- mobile only.

Responsive design is recommended because it can improve the user experience, but it is **not a mandatory cross-platform requirement**.

The actual judging emphasis is:

- UI/UX quality;
- usability;
- product functionality.

Therefore, screen coverage should be treated as a UX decision, not as a mandatory scoring checkbox.

# 8. Product Judging Rubric

Total: **100%**

| Criterion | Weight |
|---|---:|
| Product Functionality | **25%** |
| Prompting Quality | **20%** |
| Code Quality / Complexity | **20%** |
| Product UI/UX | **15%** |
| Alignment with Proposal | **20%** |

## Interpretation from official descriptions

### Product Functionality — 25%
Features should:

- work correctly;
- support the intended purpose;
- be demonstrable.

### Prompting Quality — 20%
The development process should have a clear prompting narrative showing how AI was used to build the application.

### Code Quality / Complexity — 20%
Judges evaluate the complexity/quality of the code used in the product.

### Product UI/UX — 15%
Judges consider:

- visual neatness;
- design consistency;
- ease of use.

### Alignment with Proposal — 20%
The final implementation should match the:

- idea;
- features;
- objectives;

described in the proposal.

# 17. Hackathon Kickoff Decision Constraints

When evaluating project ideas, Codex should keep these competition facts in mind.

## Hard constraints

- Must be a **web application**.
- Must be completed within the competition window.
- Must be deployable.
- Must use AI in the development workflow.
- Must include at least one AI technology as a meaningful feature/component.
- Prompt history/documentation must be preservable.
- Final implementation must remain aligned with the proposal.
- Product must be easy to demonstrate.
- Work must be original.

## High-value scoring areas

Product:

- Functionality — **25%**
- Prompting Quality — **20%**
- Code Quality — **20%**
- Proposal Alignment — **20%**
- UI/UX — **15%**

Pitching:

- Demo — **25%**
- Communication — **25%**
- AI Utilization — **20%**
- Problem/Solution — **15%**
- Product Mastery — **15%**

## Design implications supported by the rubric

When choosing between ideas, prefer concepts that can realistically produce:

- clear working functionality;
- visible AI contribution;
- a strong end-to-end demo;
- understandable user flow;
- enough technical substance to demonstrate meaningful code;
- a polished but manageable UI;
- strong consistency between proposal and implementation.

Do not choose architecture complexity purely for backend sophistication because backend infrastructure itself does not add judging points.
